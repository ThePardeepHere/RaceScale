# Development and Git workflow

[Documentation home](README.md) | [Scenario catalogue](scenarios/README.md)

RaceScale is built **one small issue at a time**, with a clean history showing why each change was made.

## Source of truth

| Information | Owner |
| --- | --- |
| Long-term objectives and technical constraints | Project blueprint |
| Task status, dependencies, acceptance criteria | GitHub Issues |
| Code and reproducible tests | Repository |
| Design rationale and educational explanations | `docs/` and implemented scenario pages |
| Actual benchmark evidence | Versioned benchmark artifacts generated by controlled runs |
| Interactive lessons | Django dashboard, when implemented |

## Proposed board states

`Backlog` → `In Progress` → `In Review` → `Done`

A GitHub Projects board can be added later. **Issues exist now, but a Projects board is not assumed to exist.** The GitHub issue backlog is [here](https://github.com/ThePardeepHere/RaceScale/issues).

## One issue, one focused change

1. Select one issue and check its prerequisites.
2. Inspect the current repository and document what actually exists.
3. Choose the smallest work unit. For a complex scenario, split failure reproduction, fix, and benchmark into separate reviewable pull requests.
4. Create a feature branch only when explicitly authorized.
5. Add targeted changes and relevant tests, with no unrelated cleanup.
6. Report commands actually run, results, constraints, and trade-offs.
7. Review and merge the change when ready, then update documentation and issue status.

Suggested branch names: `docs/scenario-catalogue`, `feat/c01-double-booking-bad-case`, `fix/c01-lock-reservation`, `test/i01-idempotency`.

Suggested commit messages: `docs: add scenario navigation`, `test: reproduce concurrent booking race`, `fix: prevent duplicate seat reservations`.

## Definition of done for an implemented scenario

- [ ] The bad case is isolated and can be reproduced with synthetic local data.
- [ ] Root cause is explained accurately.
- [ ] The good case is implemented and tested against the same requirement.
- [ ] Guarantees, edge cases, alternatives, and trade-offs are documented.
- [ ] Repeatable commands and measured results are attached if the scenario is performance-related.
- [ ] The scenario page and Django explorer point to real artifacts, when available.
- [ ] The pull request links its issue and changes no unrelated feature.

## Codex operating rule

Treat [PROJECT_BLUEPRINT.md](../PROJECT_BLUEPRINT.md) as the long-term contract and the **selected GitHub issue** as the only implementation scope. If no implementation issue has been selected, perform repository inspection only. Do not build all planned systems at once. Do not create commits or push unless explicitly authorized.

First issue: [STEP-000: Inspect local repository and environment](https://github.com/ThePardeepHere/RaceScale/issues/1). This is a discovery-only step.
